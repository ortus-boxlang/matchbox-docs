MatchBox and the JVM runtime

MatchBox aims for compatibility with core BoxLang while using an independent Rust VM. It is not the JVM runtime packaged differently. Shared language features make code portable, but JVM libraries, host APIs, and target-specific integrations need separate validation.

Check current behavior, not an old checklist.

Early guides listed JSON, file I/O, templates, and even a web server as unavailable. The repository now implements these, along with a much broader BIF surface. This guide intentionally avoids repeating stale “unsupported” lists or claiming complete parity.

Shared language foundations

  • Dynamic variables, string interpolation, operators, and control flow.
  • Functions, closures, arrow functions, and default arguments.
  • One-indexed arrays and case-insensitive struct keys.
  • Classes, inheritance, accessors, interfaces, and missing-method handling.
  • Exception handling and asynchronous programming primitives.

Use the language essentials as a starting point. Test edge cases on both runtimes when exact compatibility matters.

Standard library & integrations

The current repository includes native and BoxLang-authored BIFs for collections, strings, serialization, files, HTTP, and many other areas. Availability depends on Cargo features and the target host. Database/query, temporal, XML, and other compatibility work is actively evolving; inclusion in the source tree is not a promise of complete JVM semantics.

The CLI's bif-jni feature provides experimental Java integration on native hosts. Applications using it are no longer JVM-independent. MatchBox does not include the JVM runtime's CFML compatibility layer.

Host-specific APIs

  • The native HTTP API takes a request struct, returns a future, and produces a JSON response envelope. It is not the JVM fluent HTTP client.
  • Browser js.* access requires a browser host.
  • Web scopes exist in the web runtime; they do not appear automatically in a command-line script.
  • Cooperative fibers do not imply identical Java thread scheduling or synchronization behavior.

Write portable code

  1. Separate portable business logic from host-specific I/O and integration code.
  2. Confirm the BIFs you use are included in your build.
  3. Test the compiled artifact on the actual destination, not only in the local CLI.
  4. Pin compiler/runtime versions in repeatable builds.
  5. Report minimal reproducible compatibility differences in GitHub Issues.

The repository's changelog and compatibility tests are useful companions when evaluating a newer build.
