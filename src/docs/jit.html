The execution pipeline

  1. Parser: a Pest PEG grammar produces an abstract syntax tree.
  2. Compiler: converts that representation into VM bytecode with source location metadata.
  3. VM: executes instructions on a stack-based engine, using cooperative fibers and garbage collection.
  4. Packaging: embeds bytecode in the selected runner or browser module.

Native executables include the VM. Compilation to a standalone artifact and JIT compilation of a hot code path are separate steps.

Tiered compilation

The runtime profiles execution and only compiles eligible hot sites. The documented tiers cover:

  1. Empty-loop elimination: replace eligible repeated empty work.
  2. Numeric loops: translate supported arithmetic bodies to Cranelift IR.
  3. Array iteration: optimize eligible numeric array loops.
  4. Hot functions: compile supported function bodies and direct calls.

Not every function is eligible. Unsupported operations remain interpreted. Type guards allow optimized code to return to the interpreter when runtime values do not match its assumptions.

Size versus performance

Including a JIT increases binary size. MatchBox separates the development CLI from lean deployment stubs so that a standalone program does not automatically include the full compiler infrastructure.

Measure startup time, memory, artifact size, and throughput with your own application and target build. Tiny demonstration runners and local CLI benchmarks are not universal performance guarantees.

Build-time features

The jit Cargo feature enables Cranelift. It is included by default in the main CLI, while the VM library keeps it opt-in. See building from source to choose features deliberately.
