Hardware and toolchains matter

MatchBox compiles your script to bytecode and runs it inside ESP32 firmware. The chip, ESP-IDF environment, available memory, and runner capabilities all affect what your application can do.

Prepare your environment

  • Install the Espressif Rust toolchain using espup.
  • Install and activate a full ESP-IDF checkout.
  • Install espflash 3.3.0+ and ldproxy.
  • Install ESP-IDF prerequisites, including C build tools, Python, CMake, and Ninja.
  • Connect a supported ESP32 board and ensure your user can access its serial device.
cargo install espup
espup install
cargo install espflash ldproxy

source /path/to/esp-idf/export.sh
export RUSTUP_TOOLCHAIN=esp

Replace the ESP-IDF path with your installation. Run MatchBox in the same activated shell. Avoid layering competing ESP export scripts; the runner build prefers the activated environment.

matchbox esp32-doctor

First-time firmware flash

Create app.bxs:

println("Hello from ESP32!");

For an ESP32-S3 board:

matchbox app.bxs --target esp32 --chip esp32s3 --full-flash

--full-flash installs the runner and partition layout as well as the program. It changes the firmware on the device; back up anything you need first. Use your actual chip type, not this example blindly. If a healthy prebuilt stub is unavailable, MatchBox builds the runner locally.

Update bytecode & watch changes

matchbox app.bxs --target esp32 --chip esp32s3 --flash

matchbox app.bxs --target esp32 --chip esp32s3 --watch

After the initial full flash, --flash updates bytecode rather than replacing the full firmware. Watch mode monitors source changes and coordinates bytecode flashing with the serial monitor.

Embedded web capabilities

The embedded routed web direction is intentionally lean. Opt into its build flavor with --esp32-web. It is not the complete native app server, and route definitions should not be mistaken for a fully equivalent native transport.

The compiler rejects unsupported features such as app.listen(), disk-backed templates, static-file middleware, native webhook helpers, cookies, and sessions. Without --esp32-web, web.server() usage is rejected for this target.

Memory & hardware access

SRAM and flash are limited. Avoid large in-memory collections and measure the application on the actual board. Hardware wrappers and Native Fusion can expose GPIO, I²C, Wi-Fi, and other capabilities; available features depend on your runner and modules.

Troubleshooting

  • Missing ldproxy: install it with cargo install ldproxy.
  • Serial permission denied: check your distribution's serial-device group, often dialout or uucp. Log out and back in after changing membership.
  • WSL cannot see USB: attach the device to WSL using usbipd-win.
  • Build works, flash fails: fix serial access rather than rerunning the entire compiler as root.

The upstream ESP32 skills and embedded examples cover board-specific workflows and debugging.
